# 通用评估模型与研究依据

核对日期：2026-10-25。通过微信搜一搜实际阅读玩家文章，并交叉阅读原作者攻略。以下分开列基础机制、社区模型和项目决策策略，不能把转载数量当作独立实测次数。

## 士气：自身输出折扣

基础规则下，预计到达士气为 m（m≥0）：

`M(m) = 1 - 0.007 × max(0, 100 - m)`

| 到达士气 | 自身伤害保留 | 自身伤害降低 |
|---|---|---|
| 100 / 120 | 100% | 0% |
| 96 | 97.2% | 2.8% |
| 90 | 93% | 7% |
| 80 | 86% | 14% |
| 70 | 79% | 21% |
| 50 | 65% | 35% |
| 0 | 30% | 70% |

这是对己方造成伤害的系数，不是敌方伤害减免，也不将士气超过 100 自动转为伤害加成。特殊剧本有独立修正时先确认规则。不得未经证据把它直接乘在所有治疗、控制和特殊伤害上。

依据：官方旧版 [战斗系统](https://sgz.ejoy.com/gonglue/detail-4048.html)、[高阶战斗规则](https://sgz.ejoy.com/m/news/detail-4086.html) 的 0 和 96 士气例子；微信玩家“三战丨百科全书 / 孤独收割”2024-12-25 的 [伤害计算讲解](https://mp.weixin.qq.com/s?__biz=Mzk0MjcyNTI3Nw%3D%3D&mid=2247487799&idx=1&sn=e7e22d190be6bd08b143000d3dea819a) 也采用每点 0.7%。原文将损失百分比写进公式的方式容易误读；这里明确使用保留系数 M。

## 兵力：输出收益递减，兵池另算

微信“社恐游戏玩家部落 / 不想说话社恐人”2026-03-23 [《游戏原理分析 —— 伤害受兵力变化影响全解》](https://mp.weixin.qq.com/s?__biz=Mzk3NTA0MDE5Mw%3D%3D&mid=2247488444&idx=1&sn=6fed4168ca66cf422404ccaf07706ce8) 讨论低兵力区、对数递减与保底项，并明确引用 B 站樱谋诡计的测试；这篇不是独立复现实验。它的“半兵仍有约八成输出”等例子有属性占比假设，不适用于所有武将或战法。

微信“三战丨百科全书”上述文章提供社区公式；来源脉络可追溯到樱谋诡计的 [伤害与回复公式解析系列](https://www.bilibili.com/read/readlist/rl714525)。系列有多次修正，不能混用早期 -8 与后期 -9 版本。当前只能把它作为近似诊断，不宣称已验证服务端源码。

工具使用该社区公式的有限部分（每位武将分别计算）：

```
B(n) = ceil(100 × (log2(n) - 9))     # 仅计算 n > 2000 的区间
F(n) = min(n / 50, 100)
C(n, A) = max(A + B(n), 0) + F(n)
兵力分量比 = C(n, 0) / C(编制上限, 0)
条件输出比 = C(n, A) / C(编制上限, A) × M(到达士气)
```

A 是同一攻击类型、同一守军下的已核验属性差项，不直接等于武力。社区来源会按等级修正攻防属性；混合兵刃/谋略与多守军不能共享一个猜测的 A。工具未纳入其他增减伤、战法倍率、随机波动和特殊效果；A 未提供则不返回条件输出比。兵力分量比不能当作整名武将输出比，更不能当作队伍胜率。

例：假设每将上限 10000，n=5000，A=0，其他修正不计。C 分别为 429 与 529；兵力分量保留约 81.1%，80 士气时条件输出比约 69.7%，但兵池只剩 50%。这说明输出和存活必须分开，也说明“半兵=半伤害”和“半兵依然强所以能打完三队”都没有依据。

低兵力拐点存在来源差异：花席 2025-10-19 的 [原作者测试与简化讲解](https://news.17173.com/content/10192025/005414612.shtml) 给出约 3000 附近转缓的经验表，与上述约 2000 分段并不一致，实验等级、属性和所称伤害分量也不同。程序在 ≤2000 时不外推公式；2000 以上仍标为社区近似，绝不用它独立作“能赢”判定。保留实测原始条件，不能平均两条曲线或择一个当成官方精确式。

黄歪歪 2021-08-14 的 [玩家讲解](https://www.bilibili.com/read/cv12519537/) 强调属性、等级、科技、战法、爆发和续航共同作用，也没有给出可确保精确的统一胜率公式。由此采用逐将分析、配置隔离及完整战报校准，而不是通用常数“巨戟士需要 X 战力”。

## 通用输入约定

`sgz_assess_combat` / Python RPC `assess_combat` 仅做纯计算。阶段未知只传 `{"phase":"unknown"}`；不要先补兵力数据。战前调用示例中的 A/B/C 是任意稳定武将标识，不是限定阵容：

```json
{
  "phase": "idle",
  "observation_age_seconds": 0,
  "arrival_morale": 80,
  "morale_rule_verified": true,
  "min_total_troops": 20000,
  "heroes": [
    {"id":"A","is_main":true,"troops":5000,"capacity":10000},
    {"id":"B","is_main":false,"troops":10000,"capacity":10000},
    {"id":"C","is_main":false,"troops":10000,"capacity":10000}
  ]
}
```

此示例会计算兵池与士气影响，但因没有完整配置和可比战报返回 `insufficient_evidence`。20000 是本项目巨戟士任务政策，其他任务自行传门槛，通用默认 0。不得为凑齐示例把观测年龄填 0 或把规则验证填 true。

`context` 三个字符串建议使用实际配置的确定性 JSON 序列化（键固定排序）或其可追溯摘要：

- `ruleset`：客户端版本、赛季、剧本、模式、有效特殊规则；不是单独“PK”。
- `team_build`：每将 ID、主副位、等级、红度、实际属性、适性、战法及等级、兵书、装备、兵种、科技和当前增益。当前兵力和到达士气另填，不放入固定配置指纹。
- `target_profile`：NPC 名称空间、类型、等级、全部守军的编制/兵力/战法/兵种和特殊规则；不能只用坐标、名字或 conf_id。`defender_waves` 为已核验守军队数。

缺关键配置则不填 context；不能以“未知”字符串伪装配置完整。更改等级或配置会分组，暂不自动跨配置推断优劣；这是证据可比性的要求，并非代码只支持某个阵容。

`reports` 每条含 `id`（整次交战的唯一标识，不是单队战报号）、`source`（本地记录/可追溯战报位置）、`context`、`heroes`（初始兵力）、`arrival_morale`（进入战斗时）、`encounter_complete`、`result` 和 `completed_waves`。完整失败可以发生在首队，完整胜利必须打完全部守军。战平/中断记录不会算胜负；重复记录只计一次，重复 ID 冲突则排除。

## 综合结论的边界

程序要求当前数据不超过 300 秒；这是项目时效策略，必要时行动前再次核验，并不是当前读取能力已经实现。三个完整可比胜利也是保守经验门槛，不能报告“3/3 所以 100% 胜率”。

每份支持样本都必须被当前的**整组逐将兵力 + 士气**覆盖；不拼接多份战报的最低兵力形成一个从未赢过的配置。三次支持胜利、无同配置冲突败绩才返回 `supported_attempt`。同配置有不弱于当前条件的败绩则 `high_risk`。跨兵力与士气互有优劣、不同战法/敌人、资料缺失等返回 `insufficient_evidence`。

这提供可复核的风险建议，不模拟全部战法和随机数，不输出胜率。阵容功能与敌方控制等由 skill 结合资料分析，不能声称工具已完成战斗模拟。后续可收集合法授权讨伐的完整记录逐步扩大依据；本次评估功能不自动发起采样战斗。
