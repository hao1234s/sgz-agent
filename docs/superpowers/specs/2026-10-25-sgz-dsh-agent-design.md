**《三国志·战略版》Windows 桌面 Agent 设计稿 v0.1**

日期：2026-10-25（北京时间）  
状态：设计方案，已完成独立工程审阅；用户已选择 B 路线，尚未实施。当前目录没有现有项目，本文件是独立设计文档。

**1. 目标与已确认需求**

以 DeepSeek Harness（DSH）为基础，操作《三国志·战略版》的 Windows 游戏客户端。首版完成：电脑端准备扫码登录，用户用手机扫码授权，Agent 接续登录，并浏览大地图、保存可查询的探索记录。Agent 只控制电脑。用户已了解桌面自动化可能被识别及存在账号处理风险，并要求继续规划；这不构成官方许可，也不能据此承诺不被检测。

成功的首个演示：用户在 DSH 中指定一个角色和一个小范围的地图任务；Agent 打开二维码并等待用户扫码，确认角色后进入大地图，浏览指定范围，输出有坐标及截图依据的记录；暂停或程序重启后能重新定位并继续。

以下是设计者提出的首版默认值，用户可以调整：单账号、单窗口、简体中文界面、前台窗口化运行、固定客户区尺寸；探索指移动视角和查看可见目标详情。首个运行任务默认只处理不超过 5×5 个地图坐标点，用于验证闭环。全地图遍历、派遣部队侦察、出征、资源消耗和多账号不在本版范围内。

**2. 路线选择与取舍**

| 路线 | 做法 | 收益与代价 | 结论 |
|---|---|---|---|
| A：视觉模型直接操作 | 每轮截图交给模型，模型决定底层点击和拖动 | 较快形成演示，界面适应性较强；模型调用多，连续操作和故障定位较难 | 已讨论，未选择 |
| B：DSH＋固定流程＋视觉识别 | DSH 分配任务；本地状态流程执行；OCR/视觉识别提供事实；模型处理非固定判断 | 前期需要适配界面，但可验证、可恢复、便于记录及扩展 | 用户明确选择 |

B 的能力来源是正常游戏窗口的画面与 Windows 输入接口。DSH 的工具是本项目封装的本地能力，不是游戏官方 API。游戏客户端继续自行与服务器通信。方案不包含服务器私有协议调用、抓包重放、进程内存读取或修改、注入游戏进程、反检测或绕过客户端保护。

**3. 系统组成与技术选择**

| 组件 | 本版选择 | 职责 |
|---|---|---|
| DSH 插件 | TypeScript，独立 bundle/profile 配置 | 注册业务工具、接收自然语言任务、提供进度和结果 |
| 桌面执行器 | Python 3.11 独立进程，运行于当前交互式桌面会话 | 窗口定位、画面采集、输入串行执行、登录与探索状态流程 |
| 采集与输入 | MSS 采集可见客户区；ctypes 调用 Win32 窗口与 SendInput 接口 | 所有坐标由客户区坐标换算到当前屏幕物理坐标 |
| 本地识别 | OpenCV 定位界面锚点；PaddleOCR 通用中文 OCR | 读取按钮、坐标、角色名及详情字段；具体模型包在 P0 锁定 |
| 持久化 | SQLite＋PNG 证据文件 | 任务、观察记录、动作结果、断点及版本 |
| 模型 | 复用用户已配置的 DSH 文本模型 | 理解任务、整理结果、处理已提取的语义信息 |

执行器是交互桌面上的普通进程，不作为 Windows Session 0 系统服务运行。DSH 插件以隐藏的子进程启动它，通过标准输入输出传输带请求 ID 的 JSON-RPC 消息，诊断日志走标准错误；首版不监听网络端口。任务、数据库和模板放在可配置的数据目录中，不写入游戏安装目录。

每个游戏窗口只允许一个执行器持有控制权，所有输入由一个动作队列串行执行。跨 DSH 会话重复启动时返回“窗口已由任务占用”。插件退出、管道断开或窗口失配时，执行器停止发送输入并落盘状态。

DSH 官方提供插件、工具注册和会话事件扩展机制。实现时使用所锁定 DSH 版本的公开工具接口，业务状态独立于聊天历史保存，避免把会话日志当作地图数据库。[DSH 架构文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)

MSS 支持区域截图及与 OpenCV 配合；是否能捕获本游戏渲染画面是 P0 的实测项。若出现持续黑屏或无更新画面，记录问题并评估 Windows Graphics Capture 采集后端；不把截图接口的通用能力当作本游戏兼容性的证明。[MSS 文档](https://python-mss.readthedocs.io/stable/)、[Windows 采集文档](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture)

PaddleOCR 的 Python 包及推理引擎需要分别选择兼容版本。本版先验证本地 CPU 推理，锁定 Python、包和模型版本，不预先要求独立 GPU。[PaddleOCR 安装文档](https://www.paddleocr.ai/main/en/version3.x/installation.html)

本版不假定 DSH 当前配置的模型能够直接理解图片。常规识别在本地完成，DSH 获得结构化结果；未知页面先返回截图供人工查看并暂停。后续若增加视觉模型，需要单独选择并验证图像输入能力，不能靠纯文本模型补猜坐标。

**4. 登录流程**

流程状态依次为：客户端未打开 → 登录入口 → 二维码就绪 → 等待扫码 → 授权/加载 → 角色选择 → 角色核对 → 大地图就绪。

已经登录时，从当前可观察状态恢复，不为满足固定流程而强制登出。客户端登录 UI 若与假设不同，在适配阶段记录其实际路径；当前尚未检查该电脑上的客户端或登录界面。

| 状态/情况 | 行为 | 进入下一状态的证据 |
|---|---|---|
| 客户端未打开 | 使用已配置的绝对启动路径或用户指定的启动器启动 | 窗口的进程、标题特征和客户区匹配 |
| 二维码就绪 | 将游戏窗口置于可见位置；DSH 提示用户扫码 | 当前页面的二维码区域和登录提示可识别 |
| 等待扫码 | 本地低频检查登录页，等待用户手机授权 | 出现实际授权成功/后续页面，不以二维码消失单独判定成功 |
| 二维码过期 | 根据界面明确的过期提示点击刷新 | 新二维码和有效页面出现 |
| 选择角色 | 按配置的区服/赛区和角色标识匹配 | 进入后再次核对角色信息与地图上下文 |
| 无角色、多个同名匹配、验证失败、维护提示 | 暂停并报告当前画面/原因 | 由用户补充或处理后重新观察 |

初始运行参数：观察间隔约 2 秒；单轮等待扫码 5 分钟；二维码自动刷新最多 2 次；常规页面转移等待 30 秒、最多重试 2 次。这些是待实测调整的可靠性参数，不用于规避检测。超时后进入可恢复暂停状态，不循环刷码或反复登录。

二维码仅在原游戏窗口临时展示。登录页截图不加入地图证据库，二维码、授权票据和会话密钥不进入长期日志。手机扫码与手机上的确认由用户完成。

**5. 大地图探索的准确含义与流程**

输入包含：世界上下文、中心坐标和边长，或明确的坐标矩形；任务上限包含最大坐标点数与运行时长。世界上下文包括渠道/区域、当前赛区或服务器、赛季/剧本以及角色。角色主要用于确认登录身份，地图记录按世界上下文隔离。

首版输出是当前界面可观察到的信息，不推断迷雾下的信息、不可见守军或未展示的地图对象。对所有目标保留未知值；“未识别”不能写成“没有”。

探索步骤：

1. 确认身份与当前地图模式，设置支持的固定缩放档位，并保存锚点截图。
2. 为任务范围生成坐标点清单，按逐行折返顺序访问。首个验收任务不超过 25 个点；全图效率优化留待闭环稳定后处理。
3. P0 先检查客户端是否提供可操作的坐标定位入口。若存在，逐点输入坐标、定位并读取详情坐标，核对目标与实际一致。
4. 若无坐标定位入口，采用固定缩放和视角下的局部校准：对于可用局部仿射关系解释的地图视图，使用至少三个不共线的已确认坐标拟合，并用未参与拟合的独立点检查误差；若视图存在明显透视，至少使用四个满足非退化条件的对应点建立投影映射，仍需独立检查点验证。P0 以实际画面确定可支持的视图及误差阈值；误差必须小于目标可点击区域的容差，否则校准失败。移动视角时保留重叠区域，以新观察重新确定位置，每次拖动后都核对至少一个有明确坐标的目标。映射只负责给出候选点击位置，最终详情页坐标仍须验证；仅靠累计拖动像素不能提交定位结果。
5. 若入口和校准方案都不能建立可靠定位，本版返回“定位能力未通过”，保留已有截图和断点，停止坐标遍历；不能降级后仍宣称范围探索完成。
6. 打开目标详情，读取明确展示的坐标、名称、类别、资源类型/等级、归属等字段；具体字段以实际 UI 为准。只有同一稳定画面内能绑定到目标的字段才能入该条记录。
7. 对坐标执行格式和范围检查，复读两个已稳定的帧；再与任务坐标或校准结果比对。OCR 分数只用于筛选，不作为正确性的唯一依据。属性识别不一致时保留原文并标记待复核。
8. 原子保存观察记录、证据引用和该坐标点状态，再处理下一个点。

若地图可见但尚未打开目标详情，记为“已浏览”；完成详情核对后记为“已核验”。窗口遮挡、动画未结束、坐标冲突或无法访问的点分别记录原因。到达任务预算后正常结束本轮，输出未完成清单；只有全部点达到目标状态时才报告任务完成。

固定缩放、尺寸和地图模式是校准条件。任一条件改变后使校准失效，暂停并重建；客户端升级导致锚点不匹配也不能沿用旧点击坐标。

**6. DSH 工具边界**

下列名称是本项目拟定的工具接口，全部由插件实现，不代表游戏有同名接口。

| 工具 | 主要输入 | 输出/行为 |
|---|---|---|
| `game_status` | 可选 job_id | 当前窗口、登录状态、身份核对结果、任务进度和错误 |
| `prepare_login` | profile_id | 启动或复用登录任务，返回 job_id 与等待用户扫码等状态 |
| `observe_map` | 无 | 最新地图观察、可确认的位置及证据引用；定位未知则显式返回 |
| `inspect_target` | 世界上下文、x、y | 通过已验证导航流程查看目标，返回核验结果 |
| `explore_region` | 世界上下文、区域、预算、request_id | 创建可恢复的探索任务，立即返回 job_id |
| `pause_task` | job_id | 设置停止标志，阻止后续输入，保存断点 |
| `resume_task` | job_id | 重新校验窗口、身份、地图和校准条件后继续 |
| `export_results` | job_id、格式 | 导出 JSON 或 CSV 与本地截图索引 |

准备登录和探索都是本地持续任务，DSH 工具调用不长时间阻塞。进度在状态变化或每批目标完成时推送，平时查询本地状态；不为每帧截图调用大模型。

控制请求按 request_id 去重，跨调用重试不创建第二个任务。每条动作关联 observation_id、窗口身份、frame_version、预期前置状态及完成条件；执行前重新检查窗口和画面是否仍匹配。DSH 不直接构造任意鼠标坐标，底层点击属于经过适配的流程内部。

**7. 状态、证据与恢复**

SQLite 由执行器单点写入，至少包含：profiles（运行配置）、worlds（世界上下文）、jobs（任务与预算）、targets（目标及状态）、observations（历次观察）、actions（操作与验证结果）、checkpoints（恢复点）。SQLite 可作为无需独立数据库服务器的本地持久化方案。[Python sqlite3 文档](https://docs.python.org/3/library/sqlite3.html)

目标身份使用 world_id＋map_layer＋x＋y；首版固定一个已验证地图层。目标类别、名称及归属是观察属性，不参与去重键，避免未知类别被识别后重复建档。同一位置对象或属性变化写入新观察，不覆盖历史证据。观察字段包含 captured_at、原始 OCR 文本、已解析字段、字段置信信息、验证状态、截图引用与识别版本。数据库时间统一保存 UTC，DSH 界面按 Asia/Shanghai 展示。

PNG 先写临时文件并完成落盘，再写 SQLite 事务，防止记录引用不存在的截图。截图名称使用内容摘要或唯一 ID；中断遗留的未引用文件可在后续维护时清理，首版不自动删除用户证据。

恢复时将执行中的动作标记为“结果未知”，重新观察后决定是否需要执行。点击详情之类可重复操作也必须校验页面后再重试。数据库已确认的观察不会重复创建目标，但复查允许形成新的观察历史。

**8. 暂停与错误处理**

| 情况 | 处理 |
|---|---|
| 窗口失焦、最小化、被遮挡或尺寸变化 | 停止输入，保存当前状态；恢复时重新截图和校准 |
| 未识别弹窗、身份核对失败 | 暂停并提供可解释原因；不让模型猜按钮继续 |
| 网络断开或被登出 | 探索任务进入等待登录；登录恢复后核对同一世界再继续 |
| OCR 连续冲突 | 同一目标最多复查 2 次，之后标记待复核并按任务策略继续或暂停 |
| 停止快捷键或 DSH 暂停 | 停止队列接纳新动作，并在输入前检查取消标志；释放执行器自己按住的键/鼠标按钮 |
| 执行器退出、插件卸载、控制管道断开 | 停止输入，保留任务断点；下次启动显式恢复 |

首版提供独立于模型的停止热键，默认 Ctrl+Alt+F12，启动时检查注册是否成功。热键接收和控制管道处理不被 OCR 或模型请求阻塞；耗时识别可以完成，但取消后不得再执行其动作。暂停后的恢复由用户明确发起。

输入权限与游戏进程不匹配可能导致操作无效。先记录并解释具体兼容性问题，不自动提权或尝试隐藏输入来源。[SendInput 文档](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)

**9. 开发里程碑和验收目标**

以下是设计层的交付顺序与建议验收目标，尚非逐文件编码任务，也不是已测试结果。

| 阶段 | 交付物 | 验收依据 |
|---|---|---|
| P0：客户端适配与兼容性 | 运行配置、界面样本、截图/输入/坐标入口验证报告 | 在真实游戏窗口可连续获得有效帧；已验证动作目标与实际一致；失焦与停止热键能阻止后续输入；明确坐标导航方案能否成立 |
| P1：扫码登录闭环 | 登录状态流程与身份核对 | 在有效扫码、二维码过期、已登录三条路径中正确到达地图或给出明确暂停原因；不能把错误角色标记成功 |
| P2：小范围地图探索 | 区域任务、数据库、截图证据、CSV/JSON 导出 | 对手工标注的 25 点范围逐点核对；所有“已核验”坐标准确；至少 90% 可访问点自动完成详情核验，其余明确列出；不触发出征或资源消耗 |
| P3：恢复与集成 | DSH 业务工具、去重、暂停/恢复 | 在三个不同进度点中断并重启，均能恢复；重复请求不产生并发控制；相同目标不重复建档；失焦、未知弹窗和断线不继续盲点 |

停止响应的目标：热键触发后 1 秒内停止产生新的输入事件并释放本进程持有的输入；已发送给系统的事件无法撤回。P0 记录实际响应延迟，未达到目标前不进入长时间自动任务。

验证同时使用脱敏截图回放与有限的真实客户端检查。截图回放验证识别和状态转移，真实检查验证采集、输入、坐标定位与停止行为；二者不能互相替代。没有真实客户端验证时只报告离线通过，不报告登录或探索完成。

工期在 P0 后估算，主要取决于该客户端的截图/输入兼容性、坐标定位入口和中文 UI 识别质量。首版先记录每次任务时长、模型调用数和人工接管次数，再确定长期运行预算；目前没有证据支持具体吞吐量、模型费用或成功率承诺。

**10. 实施前的信息与可由开发者决定的细节**

开始编写通用执行器前不需要用户再回答概念性问题。实际客户端适配需要在电脑上读取或由用户指定：启动路径/窗口身份、客户端渠道和版本、当前界面语言及尺寸、目标角色/赛区，以及可用的 DSH 版本和模型配置。首次探索的坐标范围属于运行参数，可以届时指定，未指定时由用户选择当前中心附近的首个 5×5 小范围。

这些配置不在当前文档中编造。能从机器和游戏正常界面观察的内容在 P0 获取；角色有歧义时才询问用户。P0 若发现游戏没有可用扫码入口或可靠地图定位能力，应提交具体证据和替代设计，不把假设写成已实现能力。
