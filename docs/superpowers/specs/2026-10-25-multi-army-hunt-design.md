# 多队伍巨戟士调度设计

用户需求：口令“所有队伍开始打野”启动主城、分城普通作战队伍并行讨伐巨戟士。每队以实际位置检索半径 70 格；120 秒调度一轮；整次交战完成后才检查兵力/士气。低兵或低士气返回当前调动驻点，没有调动驻点才回所属城池。营帐低兵征兵，主城/分城归属队伍补满再出发。比较直接讨伐和调动后讨伐的总时间，后者更快且可行则采用。知识、任务和命令状态必须落盘。

实现选择：在现有 Python worker 内增加 SQLite 持久化调度器，客户端适配器只暴露按类型限定的观测与动作；DSH 工具启动/查看/停止/恢复任务，skill 解释授权与策略。纯 prompt 轮询不能在宿主重启后可靠恢复；多个 agent 同时操作一个客户端容易冲突，因此队伍在游戏内并行，工具执行串行。

设计约束：

- “所有”包括首次完整 roster 中本人主城/分城普通队伍，排除佣工；不自动扩展到后来新编队伍。循环持续到明确停止、资源不足或相关队伍无法确认状态；单队等待不阻塞其他队。
- 70 格采用以当前坐标为圆心的坐标圆形候选范围；路线时间与士气必须来自客户端真实预估，坐标距离只做半径筛选，不冒充路程。范围和口径在状态中返回。
- 每 120 秒先取非兵力状态；行军、战斗、战平及连续守军未结算，不查询该队兵力、战报、目标，也不触发回城。其他闲置队伍可独立检索。
- 当前巨戟士任务政策：兵力 <20000 或预计到达士气不达准备要求时回补；默认士气基准100，可按已核验配置评估。该门槛不是胜利公式。无足够体力/策书时等待，禁止购买加速或额外道具。
- 返还点与所属城池分开持久化。点位不可用不能盲目转主城命令；重新核验合法返回点。到达后先核验伤兵恢复，按实际缺口征兵；队列未结束不重复提交。
- 主城/分城直接补满指所属城池具备预备兵/资源等条件时补到编制上限；缺额要等普通征兵完成，不能把“点击补兵”视为已补满。营帐同样核验费用、队列、容量和权限。
- 路线比较 travel_seconds + prepare_seconds + attack_seconds；只选已确认可进入且有容量、预计到达士气达标的路线。调动不消耗士气须来自适用机制与当前预估，不能凭空固定加速倍数。
- 对同一目标进行持久化预占，防止多队同时领取；每次发送动作前写命令日志。超时/重启后的未知发送结果只对账，禁止重发。暂停停止调度，不撤回已出发队伍。
- 新功能开发不等于现在启动所有队伍；实机验收使用只读预览，实际战斗需用户后续口令。
- 当前执行接口存在能力缺口；未核验动作不得伪装成功。适配器按能力返回明确缺失项；生产启动须完整核验关键能力。

验证：假客户端驱动完整多队循环；战平保护；同目标互斥；更快调动；驻点回补；城池补满；队列等待；断线和重启命令对账；知识导入幂等和重开检索。实机只读验证与 fixture 测试分开报告。
